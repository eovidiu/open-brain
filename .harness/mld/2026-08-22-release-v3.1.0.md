## Mistakes
- Wrote `.harness/features.json` back with `ensure_ascii=False` on the first attempt,
  which rewrote every `\u2014` in the file to a literal em dash: a 40-line diff for a
  25-line change. Reverted and rewrote with `ensure_ascii=True` to match the file's
  existing style. Check the encoding style of a machine-written file before rewriting it.
- Assumed the failed `v3.0.0` publish was a version conflict (CLI still at 2.1.5, and
  2.1.5 was already on npm) before reading the log. The actual error was `404 PUT`, an
  authorization failure. The wrong diagnosis would have shipped a version bump and
  called the pipeline fixed.

## Learnings
- npm answers an unauthorized publish with `404 Not Found` on the `PUT`, not `401`/`403`,
  to avoid leaking whether a package exists. A 404 naming your own package on publish
  means the token, not the version.
- `.claude/hooks/` are Claude Code hooks and do not fire under omp. The project's gates
  (secret scan, git identity, scope) have to be honored deliberately in that case —
  `commit-gate.sh` can be invoked by hand with synthesized hook JSON on stdin.
- The four `workers/*` packages carry their own lockfiles and `node_modules`, and their
  suites (222 of 396 tests) are outside both `.harness/init.sh full_test` and `ci.yml`.
  CI has never run them.

## Desires
- A release gate that reads the registry, not the tag. `git tag` + `git push` currently
  produces the same local success whether the publish worked or not.
- `features.json` counters derived rather than hand-maintained; they were wrong on
  arrival and nothing noticed.
- A way to know at a glance which docs a feature's `scope` actually touched, versus
  which it merely declared. `docs/architecture.md` was declared and half-done.

## Addendum — deploy and cleanup (same session, after Ovidiu's go)

### Mistakes
- Ran the acceptance capture, then `unset K` before realising I would need a live key
  again to prove the secret deletions were safe. Raw keys are unrecoverable by design,
  so this cost a second minted key. Sequence the whole verification chain before
  minting a credential, not one step at a time.
- Assumed `POST /` was the MCP Worker's endpoint and read a 404 as a routing bug in my
  request. The handler is mounted at `/mcp`. The tell was that the unauthenticated call
  got 401 and the authenticated one got 404 — auth had already passed, so it was never
  an auth problem.
- Nearly deleted the three acceptance rows I had written to the live knowledge base as
  "cleanup". Listing recent memories first showed every prior session's acceptance
  capture still present (F004-F010), so deleting mine would have broken a standing
  convention. Check what the codebase already does before tidying.

### Learnings
- `wrangler secret delete` in a non-interactive context prints
  `Using fallback value in non-interactive context: yes` and proceeds. It does not
  need `--force` and it does not hang, which also means there is no confirmation
  safety net in a script.
- The strongest post-deploy evidence was free: a 201 whose body carries
  `embedding_status: ready` and `metadata_status: ready` proves DATABASE_URL,
  OPENAI_API_KEY and ANTHROPIC_API_KEY are all correctly bound, in one call. A bare
  201 would not have.
- A key can be minted, used and revoked without its value ever entering the
  transcript: redirect the CLI into a mode-600 temp file, `grep -oE 'obk_[A-Za-z0-9_-]+'`
  into a shell variable, delete the file in the same invocation, and print only
  `${#KEY}`. Diagnostics on failure must filter the token pattern out.

### Desires
- A `--quiet`/`--json` mode on `openbrain keys create` that writes the raw key to a
  file descriptor or path instead of stdout. Every automated use has to parse decorated
  terminal output today.
- An acceptance-suite script in the repo. The checks run this session (valid key,
  unknown key, no credential, wrong method, revoked key, both Workers' health) are the
  same ones every deploy wants, and they were reconstructed from prose in the handoff.
